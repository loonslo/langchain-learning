# Day1–Day105 功能阶段与模块划分

## 一句话看懂 105 天

这 105 天完成的是：**从调用大模型和搭建 RAG 开始，逐步做出一个可评测、可编排、可服务化、可安全上线、可自动化测试、可接企业数据并能跨 Agent 协作的客服 Copilot。**

## 一、8 个阶段总览

| 阶段 | Day 范围 | 阶段定位 | 一句话总结这个阶段做了什么 |
|---|---:|---|---|
| 1 | Day1–Day17 | 大模型与 RAG 基础 | 跑通模型调用、结构化输出、记忆和工具调用，并从零搭出具备多种检索策略的完整 RAG。 |
| 2 | Day18–Day26 | AI 质量评测 | 为 RAG 和 Agent 建立数据集、指标、裁判、回归实验、轨迹检查和发布质量门。 |
| 3 | Day27–Day40 | Agent 工作流与协议 | 用 LangGraph 把线性 Chain 升级为可分支、可循环、可恢复、可人工审批和可多 Agent 协作的工作流。 |
| 4 | Day41–Day50 | AI 应用工程化 | 把 AI 能力服务化并补齐可靠性、成本、数据、安全、容器、本地模型、测试和模型方案选型。 |
| 5 | Day51–Day60 | 客服 Copilot 核心产品 | 将前面的零散能力收敛成一条包含知识问答、会话、订单工具、人工工单和持久化的客服业务主链。 |
| 6 | Day61–Day79 | 生产化、交付与前端 | 为客服系统补齐 API、身份、幂等、安全、观测、缓存、发布、容灾、验收和浏览器工作台。 |
| 7 | Day80–Day89 | AI 自动化测试专项 | 建立从风险建模、测试数据、分层测试、Judge 校准到 CI 门禁和线上 badcase 回流的质量闭环。 |
| 8 | Day90–Day105 | 企业基础设施与跨 Agent 集成 | 用业务契约、企业数据组件、本地推理、MCP 鉴权和 A2A 协议完成企业级多 Agent 集成交付。 |

## 二、各阶段的功能模块

### 阶段 1｜大模型与 RAG 基础（Day1–Day17）

**阶段一句话：让程序先会稳定地使用大模型，再让模型能够基于外部知识回答问题。**

| 功能模块 | Day | 做了什么 | 形成的能力 |
|---|---:|---|---|
| 模型调用与 Prompt 链 | Day1–Day2 | 跑通 ChatModel、PromptTemplate、LCEL、temperature 和流式输出 | 能调用模型并控制基本回答方式 |
| 结构化输出、记忆与工具 | Day3–Day5 | 用 Pydantic 固定输出格式，加入多轮上下文和 Tool Calling | 让模型输出可被程序消费，并能使用外部功能 |
| 第一个完整聊天应用 | Day6 | 组合 Prompt、消息、记忆和工具，形成命令行 Chatbot | 从单点实验升级为最小应用 |
| RAG 最小链路 | Day7–Day10 | 完成文档加载、切块、Embedding、向量检索、生成，并手写 RAG/Agent Loop | 真正理解 RAG 的完整运行链和框架封装边界 |
| 模型原理与真实资料接入 | Day11–Day13 | 学习 Token、Attention、幻觉，处理 PDF 来源并比较切块策略 | 理解模型边界，让答案可以追溯到真实文档 |
| 高级检索优化 | Day14–Day17 | 加入混合检索、查询改写、向量库持久化、多模态和 rerank | 提升复杂问题的召回、排序和复用能力 |

### 阶段 2｜AI 质量评测（Day18–Day26）

**阶段一句话：把“感觉回答不错”变成有数据、有指标、有回归结果和能阻断发布的质量判断。**

| 功能模块 | Day | 做了什么 | 形成的能力 |
|---|---:|---|---|
| 基础指标与模型裁判 | Day18–Day19 | 手写 RAG 指标，引入 LLM-as-Judge 检查正确性和忠实度 | 能自动判断答案质量，同时认识裁判的不稳定性 |
| 评测数据资产 | Day20–Day21 | 建立结构化评测集，覆盖事实题、跨段题、拒答和引用 | 让测试问题、期望答案和证据可以版本化复用 |
| Trace 与回归实验 | Day22–Day24 | 使用 LangSmith Trace、baseline/candidate 对比和 Prompt A/B | 能定位链路问题并判断改动是否真的变好 |
| Agent 轨迹与发布门禁 | Day25–Day26 | 检查工具、参数、步骤和结果，按阈值生成失败报告 | 防止 Agent 越权，并让质量退化自动阻断发布 |

### 阶段 3｜Agent 工作流与协议（Day27–Day40）

**阶段一句话：把一条直线式调用链升级成有状态、有分支、有恢复能力并可连接多个 Agent 和工具服务的执行系统。**

| 功能模块 | Day | 做了什么 | 形成的能力 |
|---|---:|---|---|
| LangGraph 状态与控制流 | Day27–Day30 | 学习 State、Node、Edge、分支、循环、Reducer 和 ReAct | 能用状态图表达 Agent 的判断与工具循环 |
| 可靠执行与智能路由 | Day31–Day33 | 加入超时、重试、错误出口、结构化路由和 Plan-and-Execute | 让多步骤任务可规划、可控制、失败可退出 |
| 观测、恢复与人工审批 | Day34–Day36 | 建立节点 Trace、Checkpoint、上下文管理、stream 和 HITL | 能查看执行过程、暂停高风险动作并恢复运行 |
| 安全专用 Agent | Day37–Day38 | 实现受控搜索和只读 Text2SQL Agent | 让 Agent 在工具白名单和数据安全边界内完成专门任务 |
| 多 Agent 与 MCP | Day39–Day40 | 实现 Supervisor 编排，并接入 MCP Server/Client | 从单 Agent 走向多角色协作和标准化工具接入 |

### 阶段 4｜AI 应用工程化（Day41–Day50）

**阶段一句话：把本地 AI Demo 改造成有接口、可靠性、安全边界、测试和部署形态的工程应用。**

| 功能模块 | Day | 做了什么 | 形成的能力 |
|---|---:|---|---|
| API 与可靠调用 | Day41–Day43 | 使用 FastAPI 服务化，加入异步、超时、重试、成本、缓存和模型路由 | AI 能力可被其他系统调用，并兼顾质量、延迟和费用 |
| 数据与容器交付 | Day44–Day45 | 增加 SQLite 事务数据层、Trace 和 Docker 镜像 | 业务状态可落盘，运行环境可复现 |
| 本地模型与安全 | Day46–Day47 | 接入 Ollama，统一调用日志，防 Prompt Injection、PII 和密钥泄漏 | 形成云端/本地模型意识和基本安全护栏 |
| 回归测试与微调 | Day48–Day49 | 用 pytest 固定回归行为，实际完成一次 LoRA adapter 训练与对比 | 能持续防回归，并理解微调的真实成本与适用场景 |
| 技术方案决策 | Day50 | 比较 Prompt、RAG、微调、量化、蒸馏和推理优化 | 能按知识更新、成本、延迟和可控性选择方案 |

### 阶段 5｜客服 Copilot 核心产品（Day51–Day60）

**阶段一句话：把前 50 天的知识点第一次收敛成一条连续演进、真正处理客服业务的产品主链。**

| 功能模块 | Day | 做了什么 | 形成的能力 |
|---|---:|---|---|
| 客服 RAG 产品骨架 | Day51–Day52 | 拆分配置、建库、组装和业务入口，并把单文档扩展成多文档知识库 | 形成可扩展、可返回真实来源的客服知识问答 |
| 产品链评测与混合检索 | Day53–Day54 | 让离线评测复用正式 `ask()`，并把 Chroma、BM25、RRF 接进主链 | 确保测到的就是用户实际使用的检索链路 |
| 多轮会话与显式工作流 | Day55–Day56 | 加入会话隔离、追问改写，并用 LangGraph 表达客服分支 | 支持连续对话，同时让业务流程可读、可测 |
| 订单工具与可靠调用 | Day57–Day58 | 增加订单归属校验、错误分类、超时和有限重试 | FAQ 走 RAG，业务查询走受控工具，二者边界清晰 |
| 人工闭环与会话持久化 | Day59–Day60 | 无证据时创建工单，并把会话存入 SQLite | 从“拒答”升级为人工处理闭环，重启后仍可恢复会话 |

### 阶段 6｜生产化、交付与前端（Day61–Day79）

**阶段一句话：为客服 Copilot 补齐上线所需的服务、安全、观测、容量、容灾、验收和用户界面。**

| 功能模块 | Day | 做了什么 | 形成的能力 |
|---|---:|---|---|
| API、幂等与可信身份 | Day61–Day63 | 建立 `/chat` 接口、Idempotency-Key 和 JWT Identity | 服务可对外调用，写操作不重复，身份不依赖用户自报 |
| 知识更新与安全治理 | Day64–Day66 | 增量同步知识库，防直接/间接 Prompt Injection，并脱敏 PII | 知识可持续更新，用户输入、文档和日志都有安全边界 |
| 可观测、缓存与质量门 | Day67–Day69 | 建立 Trace、安全缓存和 CI 质量门 | 问题可定位、热点可优化、质量退化可阻断 |
| 容器与存储演进 | Day70–Day71 | 增加 Docker readiness，并抽象 VectorStore、准备 pgvector | 服务可交付，向量存储可替换 |
| 容量、反馈与模型容错 | Day72–Day74 | 做 p95/p99 容量判定、用户反馈 API 和模型供应商 fallback | 系统能用数据判断容量，并处理线上反馈和供应商故障 |
| 恢复、收口与最终验收 | Day75–Day78 | 验证备份恢复，统一 application 入口，绑定面试证据，执行 fail-closed 验收 | 所有能力进入真实主链，并能用证据证明可交付 |
| 浏览器工作台 | Day79 | 使用 Vite 对接 Day78 API，展示聊天、来源、订单、工单和反馈 | 后端能力变成可以操作和演示的完整产品 |

### 阶段 7｜AI 自动化测试专项（Day80–Day89）

**阶段一句话：把测试经验升级为 AI 系统专属的风险、数据、RAG、Judge、Agent、E2E、性能和线上反馈测试体系。**

| 功能模块 | Day | 做了什么 | 形成的能力 |
|---|---:|---|---|
| 风险与测试数据工程 | Day80–Day81 | 用影响×概率排测试优先级，并建立可版本化 EvalCase | 先决定最值得测的风险，再准备可信测试数据 |
| Mock、契约与不变量 | Day82 | 固定接口形状和关键业务关系 | 避免 Mock 通过但真实接口或业务规则已损坏 |
| RAG 与 Judge 测试 | Day83–Day84 | 分层测试 Recall、Precision、MRR、引用，并用人工标签校准 Judge | 能定位检索问题，也能证明自动裁判是否可信 |
| Agent 与 E2E 测试 | Day85–Day86 | 测工具轨迹、审批、API、SSE、鉴权和浏览器最终结果 | 同时验证 Agent 过程和用户真正看到的结果 |
| 安全、韧性与性能 | Day87 | 做边界输入、故障注入、重试和 p95 SLO 判定 | 验证系统不只“能通”，还可控、可靠、达标 |
| CI 与线上反馈闭环 | Day88–Day89 | 汇总分层门禁、识别 flaky，将审核后的 badcase 回流回归集 | 形成“测试→发布→反馈→新测试”的持续质量闭环 |

### 阶段 8｜企业基础设施与跨 Agent 集成（Day90–Day105）

**阶段一句话：把客服 Agent 接入真实业务契约、共享数据组件和本地推理服务，最终通过 MCP 与 A2A 完成跨 Agent 协作。**

| 功能模块 | Day | 做了什么 | 形成的能力 |
|---|---:|---|---|
| 业务意图与槽位契约 | Day90–Day93 | 建立意图分类、槽位提取、缺参追问、结构化 JSON、人工转接工作流 | 对话不再只生成答案，而是按可审计状态推进业务 |
| 企业关系数据与缓存 | Day94–Day96 | 接入 PostgreSQL、RLS、安全 SQL、Redis 缓存和限流 | 多副本系统拥有共享数据源、租户隔离和热路径治理 |
| 向量存储与本地环境 | Day97–Day98 | 完成 pgvector/Qdrant/Milvus 选型，提供 Qdrant 适配和 Compose 运维单元 | 检索基础设施可按规模选型并能本地复现 |
| 模型服务与性能门禁 | Day99–Day101 | 定义 OpenAI-compatible Provider，配置 vLLM，测 TTFT、吞吐、p95 和质量 | 云模型与本地模型可替换，部署容量由基准证据决定 |
| MCP 企业工具鉴权 | Day102 | 检查 audience、scope、最小权限和写工具审批 | Agent 只能在授权边界内调用企业工具 |
| A2A 跨 Agent 协作 | Day103–Day105 | 建立 Agent Card、任务状态机、JSON-RPC/REST/SSE，并由客服 Agent 委托订单 Agent | 独立 Agent 可以被发现、可靠调用、查询状态并完成集成验收 |

## 三、105 天形成的最终系统模块

把日期去掉后，最终作品可以理解成下面 10 个长期模块：

| 最终系统模块 | 主要 Day | 模块职责 |
|---|---:|---|
| 模型接入层 | Day1–Day3、Day42–Day43、Day46、Day74、Day99–Day101 | 统一模型调用、结构化输出、路由、降级、本地推理和性能决策 |
| 知识与 RAG 层 | Day7–Day17、Day51–Day54、Day64、Day68、Day71、Day97 | 文档摄取、检索、重排、引用、同步、缓存和向量存储 |
| Agent 编排层 | Day27–Day40、Day56、Day90–Day93 | 状态图、路由、计划、工具循环、人工审批和业务状态机 |
| 客服业务层 | Day51–Day60、Day76–Day79 | 会话、FAQ、订单、工单、反馈和统一应用入口 |
| API 与身份层 | Day41、Day61–Day63、Day86、Day102–Day105 | HTTP/SSE、JWT、幂等、MCP 权限和 A2A 协议 |
| 数据基础设施层 | Day44、Day60、Day71、Day75、Day94–Day98 | SQLite、PostgreSQL、Redis、向量库、备份恢复和 Compose |
| 安全治理层 | Day37–Day38、Day47、Day57、Day63、Day65–Day66、Day95、Day102 | 工具白名单、租户隔离、注入防护、PII、SQL 安全和最小权限 |
| 可观测与可靠性层 | Day31、Day34–Day36、Day42–Day45、Day58、Day67、Day70、Day72、Day74 | Trace、超时、重试、恢复、就绪、容量和供应商降级 |
| 评测与测试层 | Day18–Day26、Day48、Day53、Day69、Day78、Day80–Day89、Day101、Day105 | 数据集、质量指标、轨迹、自动化测试、CI 门禁和验收 |
| 产品展示层 | Day6、Day41、Day61、Day79 | CLI、API 和浏览器工作台，把底层能力变成用户可操作产品 |

## 四、最适合复习的主线

如果以后复习，不需要机械地从 Day1 重看到 Day105，可以按下面 4 条主线回看：

1. **AI 能力线：**Day1–Day17 → Day27–Day40，复习模型、RAG、工具和 Agent。
2. **产品工程线：**Day41–Day79，复习如何把 AI 能力做成客服产品并达到可交付状态。
3. **质量保障线：**Day18–Day26 → Day48/53/69/78 → Day80–Day89，复习评测、回归、门禁和反馈闭环。
4. **企业架构线：**Day90–Day105，复习业务契约、数据基础设施、本地推理、MCP 和 A2A。

## 五、最终结论

Day1–Day105 的核心并不是“学了 105 个知识点”，而是完成了这样一条能力升级路径：

> **会调用模型 → 会做 RAG → 会评测质量 → 会编排 Agent → 会做工程应用 → 会做生产级客服产品 → 会建立 AI 测试体系 → 会完成企业数据与跨 Agent 集成。**
