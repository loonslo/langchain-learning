## 1. 背景：要存的到底是什么数据

LLM 应用要落库的**不是**普通业务表，而是一张**对话日志表**，每条记录回答四个问题：

| 字段 | 回答的问题 | 对应 Day |
|---|---|---|
| `trace_id` | 用户投诉时，怎么定位到那一次请求？ | Day34 可观测性 |
| `model` / `tokens` / `cost_usd` | 这个月花了多少钱？谁最贵？ | Day43 成本 |
| `latency_ms` | p95 多少？慢在哪？ | `capstone/monitoring.py` |
| `status` / `error` | 失败率多少？失败长什么样？ | Day42 可靠性 |
| `sources` | 答案引用了哪些文档，能不能追溯？ | Day12 引用 |
| `feedback.rating` | 答得好不好？哪些该进评测集？ | Day20/26 评估 |

### 1.1 这些数据的三个决定性特征

选型的结论，几乎完全由这三条推出来。**先看清数据性质，再选存储**，反过来就是堆技术。

**① Schema 极其稳定。**
这点最反直觉：很多人默认"AI 应用 = 数据非结构化 = 该用文档数据库"。
但恰恰相反——**对话日志是整个系统里 schema 最稳定的数据**。
上面这些字段一年也不会变，因为它们是由"要回答什么运营问题"倒推出来的，
不是由模型输出决定的。真正非结构化的是 `answer` 那一列文本，
而它只是一个字段，不是一张表的形态。

**② 查询是数值聚合，不是全文检索。**
看 `daily_stats()` 实际在算什么：

```sql
SELECT substr(created_at,1,10) AS day,
       COUNT(*), AVG(status <> 'ok'), SUM(cost_usd), p95(latency_ms)
FROM conversations GROUP BY day
```

按天 GROUP BY、SUM 求和、算分位数 —— 这是典型的 **OLAP 数值聚合**。
`export_eval_set()` 则是 `conversations LEFT JOIN feedback`。
**没有一个查询需要倒排索引。** 这一条直接排除了 Elasticsearch。

**③ 需要事务和精确性。**
成本要能对账、反馈要能关联到具体对话、失败样本一条都不能丢
（因为要导成评测集）。这要求 **ACID**，而不是"最终一致"。

### 1.2 当前规模（这一条同样是决策依据）

| 指标 | 现状 | 一年后乐观估计 |
|---|---|---|
| 日请求量 | < 1000 | ~10 万 |
| 累计行数 | 几千 | 百万级 |
| 服务副本数 | 1 | 1~3 |
| 并发写入者 | 1 个进程 | 少数进程 |

**规模是选型的一部分，不是背景板。**
架构没有绝对的"更生产"，只有"匹不匹配当前规模"。

## 2. 候选方案评估

### 2.1 SQLite（当前采用）

| | |
|---|---|
| ✅ 优势 | 零部署（标准库自带，一个文件就是一个库）；完整 ACID + JOIN + 窗口函数；`capstone` 能一键跑起来演示给面试官看 |
| ❌ 劣势 | **单写入者模型** —— 这是它的硬天花板 |
| 适用边界 | 单机部署、并发写入者少、数据量千万行以内 |

**关于"单写入者"要说准确**：SQLite 支持多进程并发**读**；
开了 WAL 之后读写也不再互相阻塞（见 `day44` 的 PRAGMA 部分）。
真正的限制是**同一时刻只能有一个写事务**，而且这个锁是**基于文件的**——
一旦服务多副本部署（k8s 起 3 个 pod，跨机器写同一个网络文件），
文件锁在 NFS 上根本不可靠，数据会损坏。

> 所以准确的说法不是"SQLite 不能上生产"，而是
> **"SQLite 不能多机部署"**。这两句话在面试里的分量完全不同。

### 2.2 PostgreSQL（既定的下一步）

| | |
|---|---|
| ✅ 优势 | 真正的多写入者并发（MVCC）；和 SQLite 同为关系型，**SQL 九成通用**，迁移成本低；`pgvector` 让向量和业务数据同库（接入模板见 `capstone/vector_store_pg.py`）；生产状态存储也可统一迁移到 PostgreSQL；运维资料最多，招人也好招 |
| ❌ 劣势 | 需要独立部署（docker-compose / 云托管）；要引入连接池（`psycopg_pool`）和正式迁移工具（alembic） |
| 何时切 | 见第 4 节触发条件 |

### 2.3 Redis —— **有位置，但不是这个位置**

| | |
|---|---|
| ✅ 该用它的场景 | 会话上下文热缓存；**限流计数**（多副本下必须用它，进程内计数器一多副本就失效）；任务队列；语义缓存（Day43） |
| ❌ 不该用它的场景 | **当对话日志的真相源** |

**理由**：Redis 是内存数据库，持久化（RDB 快照 / AOF 日志）本质是
"尽量不丢"而非"保证不丢"——RDB 会丢两次快照之间的数据，
AOF 默认 `everysec` 策略也有最多一秒的窗口。

对话日志要用来**算钱、做审计、导评测集**，
不能建在一个"设计目标就不是持久化"的存储上。

> **Redis 的正确定位是热路径加速层，不是真相源。**
> 这句话在面试里能直接用。

### 2.4 Elasticsearch —— 工具用错了强项

这是最值得展开的一个，因为"日志就该进 ELK"是个很自然、也很常见的直觉。

| | |
|---|---|
| ✅ ES 真正强的地方 | 倒排索引 / 全文检索；海量日志的水平扩展写入；Kibana 现成看板 |
| ❌ 用在这里的问题 | 见下 |

**问题一：我们的查询不需要倒排索引。**
`/stats` 算的是 `SUM(cost_usd)` 和 p95 分位数 —— 数值聚合。
ES **能**做（有 percentiles aggregation），但这不是它的强项所在。
**你要为 JVM 堆调优、分片规划、冷热分层付出运维代价，
却用不上它最核心的能力。** 这是典型的用错工具强项。

**问题二：它不适合当唯一真相源。**
ES 是**近实时**的（`refresh_interval` 默认 1 秒，写入后不能立刻查到），
且没有跨文档事务。业界的成熟共识是：
**ES 作为二级索引 / 分析层，主数据留在关系库。**

**问题三：规模严重不匹配。**
ES 的优势要到千万级文档以上才体现。当前是几千条。

**那什么时候真的需要 ES？**
当出现这个需求时：*"运营要在几百万条历史对话里，
全文搜索用户抱怨过什么。"*
—— 那是倒排索引的主场，届时再引入，作为 Postgres 的**旁路索引**。

### 2.5 ClickHouse —— 如果真要上分析层，选它而不是 ES

| | |
|---|---|
| ✅ 优势 | 列式存储，做"按天聚合成本 / 算延迟分位数"这类 OLAP 查询极快（只扫需要的列）；运维比 ES 集群简单；成本更低 |
| ❌ 劣势 | 不适合高频单行更新；同样是额外的一套系统 |
| 定位 | Postgres 之后的**分析层**，不是替代品 |

**关键行业证据：Langfuse。**

Langfuse 是主流的开源 LLM 可观测平台，做的事和 `day44` 几乎逐字对应
（存 trace、observation、score、token、成本）。它的演进路径极具参考价值：

1. **v2 时期是纯 Postgres**，一路支撑到**十亿行**量级；
2. 到了这个规模，Postgres 在写入和查询上都成为瓶颈；
3. v3 把 trace / observation / score 迁到 **ClickHouse**，
   **Postgres 保留为事务型主库**；
4. 同时用 **Redis** 做缓存和队列，**S3** 存大对象。

| 层 | Langfuse v3 的选择 |
|---|---|
| 事务 / 真相源 | **PostgreSQL** |
| 分析聚合 | **ClickHouse** |
| 缓存 / 队列 | **Redis** |
| 大对象 | S3 |
| Elasticsearch | ❌ 不在架构里 |

**两个可以直接引用的结论**：
- 这条赛道最专业的玩家，分析层选的是 **ClickHouse 而不是 ES** ——
  因为负载是数值聚合，不是全文检索。
- 他们**到十亿行才开始拆**。在那之前，纯 Postgres 完全够用。

### 2.6 MongoDB —— 这套架构里没有它的位置

Mongo 的真实优势是 schemaless、嵌套文档、水平分片。
对照第 1.1 节：我们的 schema 极其稳定、数据是扁平的、规模还很小 ——
**三个优势一个都用不上**，却要放弃 JOIN 和成熟的聚合 SQL。

（Mongo 4.0+ 确实支持多文档事务，所以不能说它"做不到"；
准确的说法是**它的强项和这个场景不匹配**。）

## 3. 决策

> **短期保持 SQLite。中期迁 PostgreSQL。
> Redis 在需要时以缓存/限流层身份加入，而非替代主库。
> Elasticsearch 与 MongoDB 不进入本项目架构。**

### 决策理由（按权重排序）

**① 规模没到，提前上重型组件是负债不是资产。**
Langfuse 用十亿行证明了纯 Postgres 的天花板在哪里。
当前几千条，距离那个天花板有五个数量级。
提前引入 Redis+ES 不是"提前生产化"，是**提前把复杂度买回家**——
docker-compose、JVM 调优、分片规划、数据一致性，
每一项都要花时间维护，且都**不是 AI 应用开发的核心能力**。

**② 迁移成本已经被架构设计压到很低。**
`day44` 把**所有 SQL 都收在函数里**（DAO 边界），业务代码不碰 SQL。
换 Postgres 要改的仅限这一层：

| 要改的 | 具体动作 |
|---|---|
| 占位符 | `?` → `%s` |
| 自增主键 | `AUTOINCREMENT` → `GENERATED BY DEFAULT AS IDENTITY` |
| 迁移机制 | `PRAGMA user_version` → alembic |
| 连接管理 | thread-local → `psycopg_pool` 连接池 |
| PRAGMA | 全部删掉（Postgres 不需要） |

**正因为迁移便宜，现在就迁才不划算** —— 这个便宜是设计换来的，
不是拖延的借口，而是"可以放心晚点做"的依据。

**③ 契合转行的第一性目标。**
面试官对"AI 应用开发"候选人的考察点是 RAG 质量、评估体系、Agent 设计、
成本与可靠性工程 —— 不是"你会不会搭 ES 集群"。
把时间花在运维组件上，是**在自己不占优势的赛道上投入**。

反过来，测试背景出身能讲清"按需求选型、拒绝过度设计"，
恰恰是**很多堆技术的候选人讲不出来的**。

## 4. 迁移触发条件（写清楚，避免拍脑袋）

**满足任意一条**就启动 SQLite → PostgreSQL：

| # | 触发条件 | 底层原因 |
|---|---|---|
| 1 | 服务需要**多副本部署** | ⭐ 最硬的一条。文件锁跨机器不可靠，会损坏数据 |
| 2 | 出现持续的 `database is locked`（WAL + busy_timeout 后仍有） | 写入并发超过单写入者模型上限 |
| 3 | `conversations` 超过 **1000 万行**，`/stats` 明显变慢 | 索引维护和聚合成本上升 |
| 4 | 需要多个服务**共享**这份数据 | SQLite 没有网络协议 |
| 5 | 合规要求主从复制 / PITR 时间点恢复 | SQLite 需靠 Litestream 等外挂方案 |

**第 1 条通常最先触发**，而且它是**质变**不是量变 —— 一旦要多副本，
不管数据量多小都必须迁。

### 后续层次的触发条件

| 组件 | 触发条件 |
|---|---|
| **Redis** | 多副本部署后，进程内限流器失效 → 需要跨副本共享计数器（这也是第 1 条的连带后果） |
| **ClickHouse** | Postgres 上的聚合查询变慢，且数据量到**亿级** |
| **Elasticsearch** | 出现真实的**全文检索**需求（如"搜索所有抱怨过 X 的对话"），且 Postgres 全文索引（`tsvector` + 中文分词）已不够用 |

注意 Postgres 自带全文检索能力（`tsvector`/GIN 索引，中文可配
`zhparser`/`pg_jieba`），**在百万级规模下通常够用**。
ES 的门槛应该比大多数人以为的高得多。

## 5. 面试问答准备

> 这一节是本文档对转行最直接的价值。
> 核心心法：**能说清"为什么不用"，比"用了什么"更有说服力。**

**Q：你为什么用 SQLite？生产不都是 MySQL/Postgres 吗？**

> 因为它匹配当前规模，而且迁移成本已经被设计压低了。
> 我把所有 SQL 收在数据访问层，业务代码不碰 SQL，换 Postgres 只改那一层——
> 占位符、自增语法、连接池、迁移工具。
> 我也写清了迁移触发条件，最硬的一条是**多副本部署**：
> SQLite 是单写入者 + 文件锁，跨机器不可靠，
> 所以只要服务要起多个实例，不管数据量多小都必须迁。
> 目前是单实例、几千条数据，还没到那个点。

**Q：为什么不用 Elasticsearch 存日志？ELK 不是标配吗？**

> ELK 适合的是"海量日志 + 全文检索"。但我这张表的查询是
> 按天 GROUP BY、SUM 成本、算 p95 分位数——**数值聚合，不是全文检索**。
> ES 能做，但用不上它倒排索引的强项，却要背 JVM 调优和分片规划的运维成本。
> 而且 ES 是近实时、无跨文档事务，不适合当计费数据的唯一真相源。
> 参考 Langfuse——做同类事情的开源平台——它的分析层选的是
> **ClickHouse 而不是 ES**，主库仍是 Postgres。
> 如果将来真出现全文检索需求，我会把 ES 作为**旁路索引**加上，而不是替代主库。

**Q：Redis 呢？为什么不用它存会话？**

> Redis 会用，但定位是**热路径加速层**，不是真相源。
> 它的持久化本质是"尽量不丢"——RDB 丢两次快照之间的数据，
> AOF 默认策略也有一秒窗口。而我这张表要算钱、做审计、导评测集，需要 ACID。
> Redis 在我的规划里负责三件事：多副本下的限流计数、会话热缓存、任务队列。
> 触发点也是多副本部署——单实例时进程内计数器就够，多副本才必须共享。

**Q：那你怎么保证以后能顺利迁移？**

> 三件事。第一，SQL 全部收在 DAO 层，有明确边界。
> 第二，`test_day44.py` 有 21 个用例覆盖注入、并发写、迁移幂等、
> 游标分页、级联删除——迁移后同一套测试必须全绿，这是**回归保护网**。
> 第三，schema 用版本号管理（`PRAGMA user_version`），
> 包括处理"遗留库没有版本号"的 baseline 迁移——这个我踩过坑：
> `CREATE TABLE IF NOT EXISTS` 只保证不重复建、**不保证结构对得上**，
> 老库跑新迁移会在建索引时炸，报一个看似无关的 `no such column`。

**Q（反向提问，展示判断力）：**

> 我在这个项目里刻意没有引入 Redis 和 ES，判断是当前规模下它们是净负债。
> 想请教贵司在这块的实际情况——数据量到什么量级时开始拆分析层？
> 是走 ClickHouse 还是 ES？
