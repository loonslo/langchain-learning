## 0. 结论先行

1. **内容不缺，缺的是取舍。** 82 章 + 29 步按每章 3–5 小时、每步 4–6 小时粗算约 360–580 小时；按每周 28 小时，需要 13–21 周。2–3 个月窗口按 28 小时/周只有约 240–360 小时，装不下全部内容。核心路径应压到约 58 章、321 小时，其余降为选修或查阅。
2. **顺序要改三处。** 评测不能只当“第 3 篇”，要贯穿每一阶段；Agent 轨迹评测（3.9）应后移到 Agent 之后；5.1 的前置与章序矛盾，应先讲可靠性再讲接口。
3. **每章要从“运行 + 阅读”改成“闭卷构建 + 故障注入 + 验收”。** 企业招的不是能跑示例的人，而是能给需求、独立写出生产级服务的人。
4. **最后必须有真实上线与真实用户。** 本地原型、离线测试和“文件存在”都不等于企业证据；岗位样本反复要求“至少一个已上线项目，能讲清指标怎么测出来”。
5. **你的测试背景是主线，不是旁支。** 评测、失败分析、回归门禁、发布信心，恰恰是很多 AI 应用开发者最缺的部分。把它做成叙事，而不是只做“第 8 篇选修”。

> 这套路径按“能力”命名，不按“LangChain”命名；课程标题、框架和示例都可以换，六层能力与七道门不变。

## 1. 第一性原理：这个岗位到底在买什么

### 1.1 企业买的不是“会调模型”

企业雇 AI 应用 / Agent 开发，本质是买下面这件事：

> **把不确定的模型能力，变成可交付、可评估、可运维、可回滚的业务系统。**

拆开就是五个必须同时成立的产物：

| 产物 | 企业的问题 | 对应能力 |
|---|---|---|
| 业务问题被解决 | 这个场景值不值得做？用 prompt、RAG、微调还是 Agent？ | 问题定义、方案选择 |
| 质量可证明 | 回答对不对？引用可信吗？失败在哪一层？ | 评测、错误分析、数据建设 |
| 成本与延迟可接受 | 一次请求多少钱？p95 多少？能不能缓存/路由？ | 性能与成本工程 |
| 故障可恢复 | 上游挂了怎么办？工具超时怎么办？能否回滚？ | 可靠性、可观测性、恢复 |
| 安全与权限可控 | 会不会越权？会不会被注入？租户隔离吗？ | 安全、身份、多租户 |

只会上 LangChain 的人，五条里只能碰到第一条的一半。**课程必须围绕这五个产物组织，而不是围绕框架 API 组织。**

### 1.2 能力模型：六层，不是一张清单

```
L6 表达与交付   ── 需求、指标、架构、文档、面试、上线证据
L5 生产工程     ── API、异步、持久化、权限、可观测、部署、容量、恢复
L4 控制流       ── workflow / agent、状态、路由、工具、记忆、人工介入
L3 质量闭环     ── 评测集、judge、回归、失败分类、发布门禁
L2 上下文供给   ── 数据接入、切分、检索、重排、引用、增量更新
L1 模型接口     ── 请求/响应、结构化输出、上下文预算、工具调用、harness
L0 定位与基线   ── 目标岗位、能力自评、环境、学习与证据方法
```

三层关系：

- **L1–L2 是“让模型有输入”**：不会调用、不会给上下文，后面都是空中楼阁。
- **L3–L4 是“让系统有控制”**：评测决定你能不能看见问题，控制流决定系统能不能在不确定中保持行为边界。
- **L5–L6 是“让能力有交付”**：没有服务化、上线和表达，前四层无法变成工作能力。

### 1.3 能力形成的规律

1. **能力不是知识点的并集，而是“在约束下完成闭环”的次数。**
   看十遍 RAG 代码，不如自己从零搭一次、被召回失败打一次脸、再修一次。
2. **学习单元应该是“一个可运行闭环 + 一次失败 + 一次修正”。**
   不是“一个概念 + 一段示例代码”。失败必须是课程内容，不是意外。
3. **复杂度要按“约束”递增，而不是按“技术组件”分类。**
   单轮 → 多轮 → 检索 → 工具 → 状态 → 审批 → 多租户 → 上线；每次只加一个主要约束。
4. **评测要先行，且贯穿。**
   LLM 输出不确定，没有“怎么算对”的定义，改动就是盲改。评测不是最后一道考试，是开发方式。
5. **读代码 ≠ 会写代码。**
   企业面试让你现场写、现场 debug，不会让你解释别人的脚本。

### 1.4 由此推出的七条课程原则

| # | 原则 | 具体做法 |
|---|---|---|
| 1 | 以终为始 | 每阶段先写“企业验收什么”，再列知识点 |
| 2 | 闭环优先 | 每章一个可运行闭环，概念服务于闭环 |
| 3 | 约束递增 | 每阶段只加一个主要约束，避免同时学三件事 |
| 4 | 评测先行 | 每阶段先定义指标，再实现；评测横切 |
| 5 | 失败必修 | 每章至少 2 个故障场景，必须亲手触发 |
| 6 | 闭卷构建 | 每阶段至少一次不看参考实现从零写 |
| 7 | 证据复用 | 产出直接变成简历、面试故事、作品集 |

**要避免的反模式**：按框架罗列章节；先学完再做项目；评测放最后；只运行现成代码；追求覆盖 82 章；追逐 MCP / 多 Agent 热点；把部署留到“以后”；把学习记录写成流水账。

### 2.5 差距清单

**P0：不补就不能投**

1. **闭卷构建一个完整应用**：从需求到实现，不看参考代码。
2. **真实上线 + 真实用户 + SLO/成本证据**：本地原型不算。
3. **评测贯穿 + Judge 校准 + CI 门禁**：把现有强项变成可展示的方法论。
4. **系统设计与面试表达**：能白板讲容量、故障、取舍。
5. **修顺序**：5.1 前置、3.9 后移、选修线解耦。

**P1：决定竞争力**

6. 上下文工程与记忆（长会话、预算、压缩、长期偏好）。
7. MCP 实战（连接真实工具，处理授权与审批）。
8. 多租户 / 权限（企业项目几乎必问）。
9. 成本 / 延迟优化（缓存、路由、批处理、流式）。

**P2：加分，不着急**

12. 多模态解析、GraphRAG。
13. 前端工作台。
14. A2A / 多 Agent 深度。

## 3. 现有课程诊断

把问题归拢，是四个错位：

1. **目标与窗口错位**：课程按“覆盖完整”设计，求职按“2–3 个月形成可面试能力”约束；82 章 + 29 步装不进窗口。
2. **知识与能力错位**：课程以“读懂 + 运行”为主，企业以“给需求能独立写”为准；读代码不等于会写代码。
3. **组件与依赖错位**：评测放在 Agent 之前、选修线被代码血缘串起、5.1 前置倒置；组件的编号顺序不等于能力的依赖顺序。
4. **学习证据与企业证据错位**：离线测试、目录存在、文件检查是学习证据；企业要的是上线、真实用户、指标、故障恢复。

一句话：**课程优化了“覆盖与正确”，没有优化“在期限内形成可面试、可上手的能力”。** 这不是内容质量问题，是路径设计问题。

### 3.1 做得好的，必须保留

- **覆盖面罕见地完整**：从一次调用到 RAG、评测、LangGraph、服务化、安全、CI、压测、恢复，很多付费课都到不了这个深度。
- **每章结构清楚**：目标、前置、环境、命令、问题、概念、流程、代码导读、练习、边界，初学者能按图索骥。
- **证据文化**：离线 / 真实模型 / 部署三种状态分开记录；不把“目录存在”当“学完”。这比大多数课程严谨。
- **测试与质量是差异化**：第 3 篇、第 8 篇、capstone 的评测与门禁，正好对上企业最缺的能力。
- **双实现（flagship + capstone）**：一个偏教学分步，一个偏整合生产；对“读懂”和“看全貌”都有价值。

### 3.2 结构性问题（按影响排序）

| # | 问题 | 证据 | 影响 | 修法 |
|---|---|---|---|---|

### 4.3 为什么是这个顺序

- **L1 在 L2 前**：不理解请求/响应、token、结构化输出，RAG 的失败会看起来像“模型笨”，其实是你没控好输入输出。
- **L2 在 L3 前**：评测需要一个真实系统；没有 RAG 可评，评测只能讲抽象概念。注意 L2.9 已经先建立“最小评测”，L3 只是把评测做成系统，不是把评测全部推迟到 L3。
- **L3 在 L4 前**：Agent 行为比 RAG 更难评；先在 RAG 上练“定义对错、归因、回归”，再评轨迹。
- **L4 在 L5 前**：服务化是包装一个已经能工作的系统；先有 Agent，再谈部署。
- **L5 在 L6 前**：没有上线证据，项目故事就是“我做了个 demo”；企业不认。
- **L0 在最前**：先定目标和基线，避免“学了很多，但不知道为了什么”。

**为什么不是先 Agent 再 RAG**：企业里 RAG/上下文供给的需求更普遍，也更容易评测；Agent 增加自主性和风险，应该建立在“可控管道”之上。会 RAG 再学 Agent，迁移成本更低。

**为什么不是先微调**：微调是最后手段。绝大多数业务问题先被 prompt、检索、上下文、工作流解决；先学“何时不该微调”，再决定是否投入 GPU 和数据。

### 4.4 三条执行规则

1. **70/20/10**：70% 时间动手构建，20% 读源码/文档，10% 写总结。不要反过来。
2. **每章必须有失败**：至少 2 个故障场景，必须亲手触发并记录；没有失败的章节不算学完。
3. **评测先行**：每个 stage 先写“怎么算对”，再写实现；每个 gate 必须有可执行断言或指标。

## 7. 每章怎么写：规格模板

### 7.1 模板（10 项）

```markdown
## Lx.y 标题

- 岗位能力：对应 1–2 项 JD 能力，不写“了解/熟悉”这种不可验收的词。
- 前置：只列真正卡住学习的章节；代码血缘另标“可选还原”。
- 问题：一个真实业务场景，说明不做会怎样。
- 概念：≤5 个，每个一句话；不堆术语。
- 亲手实现：给出接口/骨架/验收，不给完整答案。
- 故障注入：≥2 个，必须能触发、能观察、能解释。
- 验收：命令 + 断言/指标 + 反例；三条缺一不可。
- 边界：明确不覆盖什么，避免“学完以为全会”。
- 产出：commit / 报告 / 图表 / 演示，能直接进作品集。
- 时间盒：2–8h；超过 8h 拆章。
```

### 7.2 验收的三种证据

| 证据 | 例子 | 不能替代什么 |
|---|---|---|
| 运行输出 | 命令跑通、日志、trace | 不能证明质量 |
| 测试断言 | pytest 通过、故障注入被捕获 | 不能证明业务价值 |
| 指标报告 | 引用正确率、p95、成本、SLO | 不能证明你理解失败原因 |

**每章至少要有前两种；每个 gate 必须有第三种。**

### 7.3 示例：把 4.5 从“读”改成“写”

**现状（4.5）**：读 3 个脚本，运行并观察轨迹；练习是“指出节点对应关系”“问一个两步问题”。验收 = 能解释。

**改写后（L4.4）**：

- **岗位能力**：工具 schema 设计、参数校验、错误处理、循环终止、轨迹记录。
- **问题**：客服要查订单、查退款政策；模型可能选错工具、传错参数、陷入循环。
- **亲手实现**：给定 `lookup_order` 与 `refund_policy` 两个 API，实现 ReAct Agent；用 Pydantic 校验参数；未知工具/超时/空结果必须有可读出口；循环上限 6 步。
- **故障注入**：① 订单不存在；② 工具超时；③ 模型请求禁用工具 `delete_order`。
- **验收**：8 条 pytest 全绿；3 个故障均返回可读错误；禁用工具调用 0 次；p95 < 3s；轨迹日志包含每步工具名、参数、结果摘要。
- **产出**：PR + 1 页失败分析（为什么模型会选错、你怎么降低）。
- **时间盒**：8h。

这不是“加难度”，而是把“能解释”换成“能交付”。

### 7.4 一章的时间盒

| 时长 | 适用 | 结构 |
|---|---|---|
| 2–3h | 概念/阅读/小实验 | 30% 读，50% 做，20% 写 |
| 4–5h | 单个能力 + 测试 | 20% 读，60% 做，20% 写 |
| 6–8h | 综合/故障注入 | 10% 读，70% 做，20% 写 |
| >8h | 拆成两章 | 不要用“长 chapter”掩盖没想清楚 |

| 评测自嗨 | 指标好看，真实用户不买账 | holdout 集 + 人工抽查 + Judge 校准 + 线上反馈 |
| 框架过时 | 学的 API 很快变 | 教 harness/状态/工具边界；固定版本；每阶段一次“换框架”练习 |
| 内容维护 | 82 章 + 29 步 + 两套实现同步困难 | 冻结 8–10 篇；capstone 为唯一生产参考；flagship 只做教材 |
| 时间不够 | 每周实际 < 20h | 用 16 周版；或 6 周压缩版先上车，再补 |
| 只会 RAG，不会 Agent | 面试问 Agent 就虚 | L4 必须闭卷写一次；轨迹评测必须做真实轨迹 |
| 只会 Agent，不会上线 | demo 很酷，一问 p95/成本就空白 | G5 不可跳过；没有上线不算完成 |

**最重要的取舍**：12 周内，**保 L1–L3 + L5 上线**，砍 L4 的多 Agent/MCP 深度和 L2 的多模态。原因是：RAG + 评测 + 上线是大多数 AI 应用岗的共同底线；多 Agent/MCP 是加分项，不是上车门槛。
