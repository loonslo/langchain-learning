# Day51–Day78 两周压缩学习计划

> 目标：把原来的 28 个学习日压缩为 14 个项目冲刺日，不删除核心功能、测试与项目证据。
>
> 适用节奏：14 个自然日，每天约 3–4 小时。第 1、2、4、12 天建议预留 4–5 小时。

## 一、压缩原则

1. 不机械地把“两天并成一天”，而是按完整业务闭环合并。
2. Day51 项目骨架、Day76 统一集成、Day77 项目表达、Day78 最终验收分别保留完整一天。
3. 每天只还原一次项目、运行一次累计测试、完成一次学习复盘。
4. 不跳过失败路径、权限边界、安全测试和“当前仍不能证明什么”。
5. 学习内容以仓库根目录下实际的 `day51/`–`day78/` 为准。

## 三、每日执行方案

### 第 1 天：项目骨架与 RAG 最小链路

- 原课程：[Day51](../day51/README.md)
- 理解 `settings → knowledge → assistant → bootstrap → cli` 的职责与调用关系。
- 跑通资料内问答、资料外拒答、来源引用和空输入保护。
- 交付：画出一次请求的数据流，并能解释检索阈值过高、过低的影响。
- 验收：还原 Day51，累计测试通过。

### 第 2 天：多文档、评测与混合检索

- 原课程：[Day52](../day52/README.md)、[Day53](../day53/README.md)、[Day54](../day54/README.md)
- 把“增加知识”到“判断质量”再到“改善检索”串成一个闭环。
- 理解稳定文档 ID、离线评测集、分层判断和 RRF 排名融合。
- 交付：新增或修改一条评测用例，观察检索策略变化是否被测试捕获。
- 验收：还原 Day54，运行 Day51–54 的全部累计测试。

### 第 3 天：多轮会话与 LangGraph 控制流

- 原课程：[Day55](../day55/README.md)、[Day56](../day56/README.md)
- 理解短追问为什么需要结合历史改写，以及会话为什么必须隔离。
- 把校验、检索、拒答和生成放进显式图流程。
- 交付：画出 LangGraph 节点、状态和条件分支图。
- 验收：破坏一个路由条件，确认对应测试失败，恢复后运行累计测试。

### 第 4 天：订单工具、重试与人工升级

- 原课程：[Day57](../day57/README.md)、[Day58](../day58/README.md)、[Day59](../day59/README.md)
- 串起“查询订单 → 上游失败 → 分类重试 → 无法自动解决 → 创建人工工单”。
- 区分可重试临时错误、不可重试永久错误和写操作风险。
- 交付：讲清订单越权保护、有限重试以及人工升级为什么是业务闭环。
- 验收：分别验证正常查询、越权、临时失败、永久失败和建单路径。

### 第 5 天：SQLite 持久化与 FastAPI

- 原课程：[Day60](../day60/README.md)、[Day61](../day61/README.md)
- 理解内存会话为什么不能跨重启，以及 HTTP 层不应承载业务逻辑。
- 跑通 SQLite 会话隔离、API 正常请求和非法请求。
- 交付：画出 `HTTP 请求 → API → 业务对象 → 存储` 的边界。
- 验收：还原 Day61，运行累计测试并手工请求一次 API。

### 第 6 天：写操作幂等与可信身份

- 原课程：[Day62](../day62/README.md)、[Day63](../day63/README.md)
- 理解客户端重试为什么可能重复创建工单。
- 区分请求正文自报的 `user_id` 与 JWT 中经过验证的身份。
- 交付：解释幂等键、重复请求结果以及身份不匹配时的处理方式。
- 验收：验证重复写入、伪造身份、无令牌和合法令牌四类路径。

### 第 7 天：知识更新与安全边界

- 原课程：[Day64](../day64/README.md)、[Day65](../day65/README.md)、[Day66](../day66/README.md)
- 串起“知识发生变化 → 增量同步 → 不可信内容检查 → 日志隐私保护”。
- 理解增删改同步、提示词注入的输入/文档双重风险，以及 PII 脱敏边界。
- 交付：整理一张安全边界表，列出输入、知识文档、输出和日志的保护措施。
- 验收：验证删除资料、恶意指令和手机号/身份证脱敏路径。

### 第 8 天：可观测性、缓存与质量门

- 原课程：[Day67](../day67/README.md)、[Day68](../day68/README.md)、[Day69](../day69/README.md)
- 串起“记录运行证据 → 安全复用结果 → 自动阻止质量回归”。
- 理解 trace、延迟、租户/知识版本缓存键和评测阈值。
- 交付：说明一次质量下降如何从指标或评测进入 CI 阻断。
- 验收：制造缓存隔离失败或低质量报告，确认测试/门禁能够发现。

### 第 9 天：容器交付与向量库迁移契约

- 原课程：[Day70](../day70/README.md)、[Day71](../day71/README.md)
- 理解“本机能运行”与“可复现交付”的区别。
- 理解向量存储协议、pgvector schema、迁移能力与真实完成迁移的区别。
- 交付：记录镜像启动条件、readiness 条件、迁移步骤和回滚边界。
- 验收：运行启动检查及向量存储契约测试；环境允许时构建容器。

### 第 10 天：容量判定与用户反馈闭环

- 原课程：[Day72](../day72/README.md)、[Day73](../day73/README.md)
- 理解单次响应时间不能代表系统容量。
- 把用户 bad case 送入可审查队列，而不是直接污染评测集或知识库。
- 交付：写出容量合格条件，以及反馈进入评测集前的人工复核步骤。
- 验收：验证容量阈值通过/失败，以及正负反馈入队路径。

### 第 11 天：模型降级与备份恢复

- 原课程：[Day74](../day74/README.md)、[Day75](../day75/README.md)
- 理解供应商临时故障时的 fallback，以及备用模型也需要独立质量评测。
- 理解“生成了备份文件”不等于“备份能够恢复”。
- 交付：整理模型故障和数据故障两条恢复流程。
- 验收：模拟主模型失败，并实际验证备份文件可读取、可恢复。

### 第 12 天：统一业务应用

- 原课程：[Day76](../day76/README.md)
- 重点阅读 `application.py`、`runtime.py` 与修改后的 `api.py`。
- 验证此前独立组件是否真正进入同一条请求链路，而不只是分别存在。
- 交付：画出最终系统架构和一次完整请求的时序图。
- 验收：至少覆盖 FAQ、订单、人工升级、身份失败和依赖失败五类端到端路径。

### 第 13 天：项目证据与面试讲解

- 原课程：[Day77](../day77/README.md)
- 把每个项目主张绑定到代码、测试或运行结果，避免只有功能罗列。
- 准备 60 秒简介、5 分钟项目讲解和 3 个技术深挖问题。
- 交付：完成项目故事，并能清楚区分“本地验证”“迁移契约”和“生产上线”。
- 验收：运行证据检查；任何没有证据的能力不得写成已完成。

### 第 14 天：最终验收与复盘

- 原课程：[Day78](../day78/README.md)
- 还原最终项目，运行全部测试并演示关键正常/失败路径。
- 从 RAG、Agent、工程化、安全、测试五个角度进行模拟面试。
- 交付：最终 README、验收记录、项目边界和下一版本路线。
- 验收：Day78 完整测试通过，项目能运行、能解释、能展示证据。

```markdown
## 第 N 天打卡

- 对应旧 Day：
- 今天解决的业务问题：
- 完整调用链：
- 最重要的代码变更：
- 正常路径测试：
- 失败/越权/安全路径测试：
- 我主动破坏了什么，哪条测试失败：
- 当前证据能证明什么：
- 当前仍不能证明什么：
- 60 秒项目表达：
```

## 七、使用注意

- 两周指 14 个自然日；如果只有 10 个工作日，不建议继续硬压。
- 如果某天累计测试没有通过，不带着失败进入下一天。
- 第 2、4、7、8 天内容较多；第 10、11 天可用于补齐前面的理解和测试。
- `capstone/docs/day51-78-roadmap.md` 与当前 `day51/`–`day78/` 的主题映射不完全一致；本计划按实际 Day 目录编排。
- 压缩的是重复操作和课程切分，不是安全、测试、失败路径与项目表达。
