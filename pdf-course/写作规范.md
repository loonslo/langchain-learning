# 写作规范（改稿必须遵守）

改这份教程时的统一口径。**改任何一章之前先读这一页。**

## 一、语气：和读者坐在同一侧

作者不是老师，是「先走过一遍的人」。所以：

| 不要 | 改成 |
| --- | --- |
| 「记住这个三段结构。」 | 「后面每一个新概念，落点都在这三个位置之一。」 |
| 「密钥必须只放 .env。」 | 「密钥放在 .env 里，提交到公开仓库时就不会被扫到。」 |
| 「这是新手第一周最常见的错误。」 | 「密钥写进代码的代价是：提交到公开仓库后通常几分钟内就会被盗用。」 |
| 「所有分类任务都要留一个「其他」类别。」 | 「留一个「其他」类别，模型才有地方说「我不确定」。」 |
| 「以为模型会自己执行函数。不会。」 | 「模型其实不执行函数，它只输出「想调用谁、参数是什么」。」 |
| 「宁可多问一句，也不能猜错了退款。」 | 「多问一句的代价是慢一拍；猜错的代价是退错钱。」 |
| 「你现在应该能说清……」（拷问式） | 「这一节留下的几个点：……」（陈述式） |

**具体禁用/替换清单：**

- 禁：`必须` / `一定要` / `绝不能` / `千万不要` / `宁可…也不要`（改成陈述后果）
- 禁：`记住…` / `注意…` / `请…`（改成平述）
- 禁：道德判词——`最常见的错误` / `最危险` / `最忌讳`（改成「代价是…」）
- 禁：`不会。` / `错了。` 这种短促否定开场
- 禁：反问句当小标题或结论
- 慎用：`你`。描述读者会遇到的情况可以用，但不要变成命令句的主语
- 少用感叹号

**不是不许有判断。** 可以明确说「这样做的代价是 X」，只是不做道德审判、不居高临下。

## 二、结构：图先说话，文字收口

**每一节至少一张图。** 图承担「结构」，文字只承担「为什么」和「代价」。

- 抽象名词成对出现（向量/关键词、fail open/fail closed、MCP/A2A）→ `compare()`
- 有先后顺序（检索链路、请求路径、委托流程）→ `flow()` 或 `vflow()`
- 有循环（Agent、rerank、重试）→ `loop()`
- 有层级或边界（租户/用户/线程、接口/业务/数据）→ `layers()`
- 有生命周期（任务状态、工单流转）→ `states()`
- 按产品构建、上线和交付阶段组织 → `timeline()`
- 跨服务来回（客服 Agent ↔ 订单 Agent）→ `seq()`
- 数字对比（耗时、成本、召回率）→ `bars()`
- 并列的几类东西（四类失败、三种方案）→ `cards()`
- 一次请求的成本/耗时构成 → `stack()`

图的写法见 `content/dia.py` 顶部注释。**图题写结论，不写主题**：
- 不好：「RAG 流程图」
- 好：「检索把「不知道」变成「查到了再答」」

**配图之后要删文字。** 图已经把结构讲清楚了，段落就不要复述一遍。
判断标准：把这段文字删掉，读者看图还能不能懂？能懂就删。

## 三、框的用法（框标题也要去说教）

| 组件 | 原标题 | 改后标题 | 内容写法 |
| --- | --- | --- | --- |
| `KEYPOINT` | （无标题） | 保持无标题 | 一句陈述，不是命令 |
| `VERIFY` | 怎么验证它生效了 | 怎么知道它生效了 | 描述可观察的现象 |
| `TRAP` | 常见的错法 | 容易出问题的地方 | 描述「这样做的代价」 |
| `CHECKLIST` | 学完自检 | 这一节留下的几点 | 名词短语，不是问句 |
| `SIDE` | 白话：X / 前置知识 | 保持 | 平述，别用「你可以理解成」 |

框的数量要克制：一节最多两个框。框多了会把页面切碎，也把读者推回「被讲授」的位置。

## 四、内容纪律

- **不照搬代码注释**，要写「为什么这么写」和「不这么写会怎样」。
- **不虚构**。代码位置、运行命令、阈值都要能在仓库里找到对应。
- **前后呼应**：跨章引用写「第 N 章」，改结构后要全文回查（见 `huashu-report-windows` 第七节）。
- **诚实标注边界**：没做的、不确定的，直接说没做。
