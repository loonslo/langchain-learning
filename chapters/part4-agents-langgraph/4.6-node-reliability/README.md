# 4.6 节点可靠性：失败之后如何继续

[全书目录](../../README.md) · [上一章 4.5](../4.5-react-agent/README.md) · [下一章 4.7](../4.7-structured-routing/README.md)

- **目标**：让节点在出错时不崩，用四道防线区分可重试的错误和不可重试的错误。
- **前置**：4.5。
- **环境**：大部分离线；【三】需要真实模型，没配 `DEEPSEEK_API_KEY` 时自动跳过。
- **命令**：`python tools/run_chapter.py 4.6`

## 问题

4.5 的 Agent 能跑，但所有工具都“一定成功”。真实世界会有搜索超时、数据库连不上、模型限流（429）、工具抛异常。默认情况下，节点里一抛异常整张图就崩了，用户拿到 500，这在生产里是事故。

## 概念

核心原则：区分**可重试的瞬时错误**（网络抖动、限流、超时）和**不可重试的确定错误**（参数错误、无权限）。前者值得重试；后者重试一百次也没用，应快速失败并降级。

四道防线，从轻到重：

1. **try/except + fallback**：捕获异常，返回“降级但可用”的结果，图继续运行。
2. **`RetryPolicy`**：瞬时错误自动重试几次。
3. **`ToolNode` 的工具报错不崩**：让工具异常作为 `ToolMessage` 回喂给模型，模型自己换个办法。
4. **超时护栏**：给慢节点设上限，别让一个卡死的工具拖垮整条请求。

## 流程

`node_reliability.py` 的四段演示：

1. 【一】`flaky_fetch` 有一半概率抛异常，`robust_node` 捕获后返回降级结果；连续调用三次，失败的那几次图也不会崩。
2. 【二】前两次失败，`RetryPolicy` 自动重试到成功。
3. 【三】让模型计算“10 除以 0”，工具报错回喂给模型，由模型解释（需要模型）。
4. 【四】`with_timeout`：快调用拿到真实结果，慢调用触发降级。

## 代码导读

[node_reliability.py](node_reliability.py)：按【一】到【四】的顺序读，每段都是一个 `build_*` 或演示函数；重点看【二】怎样把“前两次失败”的行为固定下来，方便复现（`random.seed(0)`）。

## 练习

1. 把【二】的重试次数改小，观察最终结果如何变化。
2. 让某个工具抛出“参数错误”，判断它该不该重试，并说明理由。
3. 给【四】的超时设一个更短的值，观察哪次调用触发了降级。

## 运行与边界

- 降级结果要让用户或下游知道它是降级的，不能伪装成真实数据。
- 重试只适用于幂等或只读的操作；有副作用的写操作需要幂等键或人工确认。
- 4.9 让这些失败“查得到”。
