# 4.15 框架取舍：先写需求，再选择工具

[全书目录](../../README.md) · [上一章 4.14](../4.14-supervisor-fanout/README.md) · [下一章 5.1](../../part5-production/5.1-serve-fastapi/README.md)

- **目标**：学完 ReAct、状态图和 Supervisor 之后，能根据业务约束选择编排层，而不是按名字的流行程度。
- **前置**：4.1–4.14。
- **环境**：无代码，以文字和选型工作簿为主。

## 问题

学会几个框架以后，常见的困惑是：下一个项目到底用谁。选择应该从流程需求出发：步骤是否固定，是否需要可恢复的状态，是否以严格的类型和工具契约为核心。

## 概念

模型 SDK 处理直接请求；链处理组合调用；图处理显式状态与分支；Agent 框架提供工具循环和相关边界。框架提供机制，业务权限、事实来源和验收仍由应用自己设计。

框架功能会变化，下表于 2026-09-28 对照官方说明，不要求把每个框架都安装一遍。

| 方案 | 官方文档描述的能力 | 本课程如何使用 |
|---|---|---|
| 裸 SDK + 自己的循环 | 应用自行管理请求、工具执行与状态 | 2.5 理解运行时责任；错误、预算与恢复自行定义 |
| LangChain | 模型与工具集成、预置的 Agent 架构 | 先快速完成标准工具循环，再按需求补业务边界 |
| LangGraph | 明确的状态编排、持久化、流式与人工介入 | 用于需要检查节点、条件边和恢复的工作流 |
| Pydantic AI | 带类型的模型 / 工具交互与依赖注入 | 作为重视 Python 契约与可测试依赖的对比对象 |

LangChain 的 Agent 构建在 LangGraph 运行时之上，两者可以组合。功能说明见 [LangChain 概览](https://docs.langchain.com/oss/python/langchain/overview)、[LangGraph 模式与工作流](https://docs.langchain.com/oss/python/langgraph/workflows-agents)、[Pydantic AI 官方介绍](https://pydantic.dev/docs/ai/overview/) 与 [依赖说明](https://pydantic.dev/docs/ai/core-concepts/dependencies/)。表中的课程选择是教学取舍，不是性能排名。

MCP 负责工具接入协议，A2A 负责 Agent 间协作契约，它们不是上表中的编排框架。换工具传输协议不必重写所有业务规则，但也不会自动获得鉴权、租户隔离或可靠性。

## 流程：怎样做一次选择

1. 列出任务的步骤、状态和失败要求。
2. 判断普通函数是否已经足够。
3. 需要分支与恢复时评估图。
4. 需要模型动态决策时评估 Agent。
5. 最后检查依赖、测试和团队的维护能力。

## 练习

从下面三个场景中选一个，先写要求，再选方案：固定的检索问答；带有限工具调用的订单查询；主管审批后可恢复的工单处理。

每个候选方案都回答同样的问题：

1. 状态由谁维护，哪些字段允许节点改写？
2. 如何停止循环，超时和重试在哪里设置？
3. 工具的副作用怎样授权、幂等和审计？
4. 暂停后由谁保存状态，恢复会重跑什么？
5. 如何用替身测试拒答、错误、隔离和恢复？
6. 切换框架后，哪些业务代码能保留，哪些运行时契约要重新验证？

先复跑 4.1 的离线控制循环，再读 4.10、4.11 的持久化与人工介入。对于审批场景，优先复用本仓库的 LangGraph 练习，因为已有显式状态与恢复的验收；这项判断仍需要你自己的失败实验支持。

## 产物与验收

产物是 [选型工作簿](workbook.md)：写明必须满足的能力、选中的方案、至少一个替代方案、淘汰依据和验证方法。不要仅用“更流行”或“代码更短”作结论。

能说明框架替你做了哪些工作、仍由应用负责什么，就完成了本章。没有安装对比框架、没有真实压测时，不要填写“兼容性与性能已验证”。
