# 3.4 评测数据建设：把业务覆盖写成样本

[全书目录](../../README.md) · [上一章 3.3](../3.3-llm-judge/README.md) · [下一章 3.5](../3.5-eval-dataset-ragas/README.md)

- **目标**：把评测集当作数据资产来造：先定稳定的 schema，再写第一批样本，存成 JSON。
- **前置**：3.2。
- **环境**：离线。
- **命令**：`python tools/run_chapter.py 3.4`

## 问题

评测集只有几条示范时，改动再多也说明不了什么。评测集是 RAG 的自动化回归用例库，需要有固定的结构、覆盖不同题型，并且能和代码分开管理。

## 概念

- **schema**：每条样本的字段约定：`id`、`question`、`reference`（标准答案）、`keywords`（答案必须出现的核心词）、`expect_source`（应命中的来源）、`type`（题型）、`should_refuse`（是否应拒答）。
- **题型覆盖**：本章写两类最基础的题：事实问答（答案在单句内，考检索得准、答得对）和跨段落问答（答案要拼多处，考召回全、会整合）。拒答题和引用题在 3.5 补齐。
- **存成 JSON**：与代码解耦、可版本管理、能被 3.2、3.3、RAGAS、pytest 共用。
- **题目基于短文档**：所有题目与标准答案都来自 `chapters/shared-data/test_doc.txt`，改动该文档会让评测集失效。

## 流程

1. 在代码里定义 `SCHEMA_FIELDS` 与第一批 15 条样本（10 条事实题 + 5 条跨段落题）。
2. `validate` 检查每条字段是否齐全、`id` 是否重复：评测集脏了，后面的评测都白做。
3. 写出 `chapters/shared-data/eval_set.json`，打印各题型数量。

## 练习

1. 再加 5 条“问法刁钻”的题（同义换词、口语化、含错别字），看检索还稳不稳；这些题最能暴露召回短板。
2. 给某条样本删掉一个必需字段，确认 `validate` 能报错。
3. 对照 `test_doc.txt`，检查每条标准答案是否真的能在文档里找到依据。

## 运行与边界

- 样本由人工编写，覆盖面有限，不能代表真实用户的提问分布。
- 本章只生成评测集，不调用模型，也不评估系统。
