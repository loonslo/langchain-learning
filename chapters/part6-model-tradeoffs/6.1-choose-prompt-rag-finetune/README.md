# 6.1 Prompt、RAG 与微调：问题不同，方案也不同

[全书目录](../../README.md) · [上一章 5.8](../../part5-production/5.8-pytest-regression/README.md) · [下一章 6.2](../6.2-lora-finetune-optional/README.md)

- **目标**：从需求约束出发，在 Prompt、RAG、微调之间选起始方案，并知道每种方案上线前要验证什么。
- **前置**：2.3（RAG）、1.3（结构化输出）。
- **环境**：离线，不调用模型。
- **命令**：`python tools/run_chapter.py 6.1`

## 问题

模型答得不对时，常见的冲动是“那就微调一下”。但问题的原因不同，方案也不同：模型不知道私有知识，微调补不上；输出格式不稳定，堆更多文档也解决不了。选型要从可验证的业务目标出发，而不是套一句固定的口诀。

## 概念

- **Prompt**：定义当前任务、边界和输出契约，但不会可靠地补齐模型不知道的私有知识。
- **RAG**：推理时注入外部知识，适合知识会变化、需要引用、或需要按权限取数的场景。
- **微调**：主要改变稳定的行为、格式或领域模式；它不是动态知识库，也不天然提供引用。
- **三者不是互斥产品，也没有固定的成本排序**。选型时同时看质量、时延、吞吐、权限、更新频率和总拥有成本，再用离线评测和线上观测验证。

## 流程

`decide()` 把需求约束翻译成起始方案：

1. **知识类需求**（知识经常变化、需要引用、模型不掌握所需知识）→ 需要检索。
2. **行为类需求**（需要固定风格或格式），并且样本充足、训练可行 → 可以微调。
3. 两类都满足 → RAG + 微调；只满足其一 → 对应方案；都不满足 → 先用 Prompt 建立可评测的基线。
4. 无论选哪个，上线前的检查项包括：评测集上比较质量、拒答和引用；测 p95 时延、吞吐和单次请求总成本；私有知识检索前做租户和文档权限过滤。选了微调时，还要保留基座对照组，并验证数据许可、漂移与回滚。

文件末尾还列出大模型输出能力的四个可组合维度：内容、传输、契约、动作。它们不是五个互斥的类别。

## 代码导读

[model_strategy.py](model_strategy.py)：先读 `decide` 的六个参数和两个中间变量 `needs_retrieval`、`can_fine_tune`，再看返回的 `Decision`（方案、理由、检查项）。`recommend` 是位置参数的简化入口，假设“知识常变”就意味着“模型不掌握所需知识”，需要区分时直接用 `decide`。

## 练习

1. 给一个“每日更新的政策问答”和一个“固定格式的分类任务”各写一份需求，先预测建议的方案，再运行规则验证。
2. 找出规则建议 RAG，但你认为应该微调的场景；说明你还缺什么证据。
3. 为你建议的方案写出三条上线前的验证项，并说明用哪个评测集或指标检查。

## 运行与边界

- 规则建议只是起始方案，不是对任何模型或业务的性能承诺；昂贵的方案需要先有可验证的收益假设。
- 微调的实操见 6.2（选做）。
