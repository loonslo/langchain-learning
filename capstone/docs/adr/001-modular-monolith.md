# ADR-001：采用模块化单体和唯一业务服务入口

- 状态：Accepted
- 决策日期：2026-08-03

## 背景

项目同时包含 RAG、受控数据工具、Agent、长期记忆、安全、评测和运行能力。若每个教学日保留一套独立调用链，API、CLI、评测和测试会逐渐产生不同语义，也无法证明某项能力已经进入真实服务。

## 决策

第一版采用模块化单体：

- `AssistantService` 是用户请求的唯一业务入口。
- API、CLI、评测和 E2E 测试调用同一个服务契约。
- 检索、查询工具、工作流、记忆、安全和 provider 通过显式依赖注入组合。
- `dayXX` 文件只描述当天项目事件、运行验收并输出证据，不保存生产业务逻辑。
- Chroma/pgvector、内存/持久化 Store 等变体位于接口之后，通过配置或 feature flag 切换。

## 原因

- 单人学习项目不需要微服务的网络、部署和一致性成本。
- 模块边界仍可训练接口设计、依赖倒置和契约测试。
- 唯一入口能避免“评测通过但线上路径不同”的假证据。
- 后续只有在团队所有权、独立扩缩容或隔离要求出现时再拆服务。

## 代价

- 同一进程内的重型模型和租户索引仍需控制内存与并发。
- 模块间错误边界需要主动设计，不能依赖网络天然隔离。
- pgvector、Redis、外部审核器等依赖仍须做真实集成测试。

## 重新评估条件

- 摄取和在线查询需要独立扩缩容。
- 高风险工具必须运行在单独安全域。
- 多团队需要独立发布节奏。
- 单体资源竞争无法通过队列、进程池或部署拆分解决。
