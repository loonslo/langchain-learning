# 5 分钟项目讲解（Day70）

> 原则：只讲仓库和报告能证明的事实。括号里的“边界”也要主动说，它比夸大数字更能体现工程判断。

## 0:00–0:30：定位

我做的是一个企业知识库问答与自动化评测平台。重点不是聊天界面，而是把检索、权限、回归、安全和运行指标放到同一条可验证链路里。这延续了我的测试工程背景：把概率性模型能力转成有边界、有失败信号的系统。

## 0:30–1:40：数据、问答和权限

数据层支持 TXT、Markdown 和 PDF。文档经过确定性切分后同时进入向量检索与 BM25，两路结果做融合；应用只根据真实召回文档生成来源，避免模型自己编文件名。

文档变化通过 SHA-256 manifest 做增量同步，新增、修改、删除只处理差异，确定性 chunk ID 保证全量构建和增量构建一致。

企业数据不能只靠 Prompt 保密。当前实现会在向量查询发出前带上 ACL，BM25 也只看授权子集；租户有独立持久化目录，JWT claims 提供用户、租户、部门和角色。测试覆盖默认拒绝、跨租户拒绝和查询前过滤。

## 1:40–3:00：评测和 CI

我把评测集作为版本化回归输入。当前是 6 条基础用例：4 条可回答事实、2 条应拒答问题。2026-07-29 用本地配置的 DeepSeek 实跑结果是关键词命中 4/4、拒答 2/2、失败 0。

我会明确说明这个数字的边界：它证明当前 6 条回归没有退化，不代表真实业务总体准确率。下一步需要从真实问法扩充权限、跨文档、引用一致性和对抗场景。

GitHub Actions 会运行生产边界测试、真实模型回归和质量门禁，失败时上传报告。要真正阻止合并，还要在仓库设置里把该检查设为 required；工作流文件本身不等于分支保护已经开启。

## 3:00–4:10：服务化、监控和性能

FastAPI 接口包含 Bearer 认证、租户限流、请求 ID、输入边界、响应脱敏，以及租户/用户/角色/模型/知识版本感知的 TTL 缓存。监控按租户统计 p50/p95/p99、错误率、token、成本和缓存命中率；样本不足不会被报告成健康。

我还把 Locust 对准当前认证 API。一次本地假上游冒烟结果是 2 用户、5 秒、50ms 模拟上游，23 个请求、0 失败、6.033 rps、聊天 p95 80ms、服务端 p95 51.9ms。这个结果只证明压测工具链和指标对照可用，不是系统容量结论；生产定容需要更长稳态和逐级加压。

仓库已有 Dockerfile、部署前检查和说明，但我的本机当前没有 Docker，因此没有验证镜像构建，也没有公网地址。我会说“具备部署准备”，不会说“已经上线”。

## 4:10–5:00：取舍和下一步

当前选择租户独立 Chroma，是为了低成本完成本地闭环；规模、并发、备份或统一运维要求上升时，再用 `capstone/vector_store_pg.py` 的 pgvector 路径做真实迁移验证。内容安全当前有本地规则和外部审核器接口，但完整合规仍需要具体服务、人工复核和法务确认。

Agent 部分演示了 LangGraph 人工审批中断，但 checkpointer 仍是内存实现；MCP 只在独立学习文件中练习，没有纳入毕业项目。这两项是明确的后续工作，不包装成已交付。

一句话收尾：我能做的不只是“让模型回答”，而是为身份、知识、模型调用和质量回归建立可测试的边界；哪些已经验证、哪些仍是假设，我都能给出证据。

## 可让面试官继续追问的三个点

1. 为什么 ACL 必须在向量查询和 BM25 建索引前生效，缓存键又为什么包含身份与知识版本。
2. 为什么 6/6 通过仍不能说“准确率 100%”，以及如何从线上失败扩充评测集。
3. 客户端 p95 与服务端 p95 为什么只能做排队线索，不能直接相减后当作精确排队时间。
